# AGENTS.md — Технічна документація проєкту "Window Layout Manager"

## 1. Загальна ідея

Утиліта для Windows, яка керує розташуванням та компоновкою вікон на робочому
столі (у т.ч. на кількох моніторах). Програма повинна вміти:

- запам'ятовувати список запущених програм, шлях до їх виконуваних файлів,
  положення та розмір їхніх вікон (знімок поточного стану — "сесія");
- за запитом користувача відновлювати цю сесію: запускати потрібні програми
  (якщо вони не запущені) і розставляти їхні вікна точно на ті самі
  координати з тими самими розмірами, з якими вони були збережені.

Кінцева мета — швидке відновлення робочого простору (workspace) після
перезавантаження, зміни конфігурації моніторів, або перемикання між
різними "профілями" розкладки вікон.

## 2. Стек технологій та обмеження

| Параметр | Значення |
|---|---|
| Мова | C++ (сучасний стандарт, C++17/20) |
| API | Win32 API (WinAPI) напряму |
| Заборонено | .NET, WinForms, WPF, UWP, C++/CLI |
| Результат збірки | Один-єдиний `.exe` файл |
| Зовнішні залежності | Жодних сторонніх `.dll`, окрім стандартних системних (`kernel32.dll`, `user32.dll`, `gdi32.dll`, `shell32.dll`, `psapi.dll`, `dwmapi.dll` тощо) |
| Формат даних сесії | `.json` (основний) або `.xml` (альтернатива) — файл лежить поруч із `.exe` |
| JSON-бібліотека | Header-only бібліотека (наприклад, `nlohmann/json`), яка **компілюється прямо в exe** і не потребує runtime `.dll`. Якщо це неприйнятно — власний мінімальний JSON-парсер/серіалізатор без зовнішніх залежностей |
| Лінкування | Статичне (`/MT` замість `/MD`), щоб не залежати навіть від MSVC runtime `.dll` |
| Розрядність | x64 (з можливістю пізніше зібрати x86 за потреби) |

### Ключові WinAPI-механізми, які використовуються в проєкті

- `EnumWindows` / `EnumChildWindows` — перелік топ-рівневих вікон;
- `IsWindowVisible`, `GetWindowTextLength/GetWindowText` — фільтрація видимих вікон і отримання заголовків;
- `GetWindowRect` / `GetClientRect` — розмір і положення вікна;
- `GetWindowThreadProcessId` + `OpenProcess` + `QueryFullProcessImageName` (або `GetModuleFileNameEx` з `psapi.dll`) — визначення шляху до `.exe`, з якого запущено вікно;
- `GetWindowLong(GWL_STYLE / GWL_EXSTYLE)` — визначення стану вікна (звичайне/згорнуте/розгорнуте), наявність рамки тощо;
- `EnumDisplayMonitors` / `GetMonitorInfo` — перелік моніторів та їхніх координат для коректної роботи у multi-monitor середовищі;
- `SetWindowPos` — встановлення позиції та розміру вікна під час відновлення;
- `CreateProcess` — запуск програми зі збереженого шляху;
- `WaitForInputIdle` — очікування готовності процесу перед позиціонуванням (частково вирішує проблему splash screen).

## 3. Порядок роботи над проєктом

**Головне правило процесу:** розробка ведеться виключно покроково.
Після завершення кожного етапу — зупинка, демонстрація/пояснення
результату та **очікування явного підтвердження від користувача**
("ок", "продовжуй", "далі" тощо) перед переходом до наступного етапу.
Без підтвердження наступний етап не починається.

### Етап 3.1 — Мінімальний список видимих вікон

**Мета:** створити `.exe`, який відкриває власне Windows-вікно (звичайне
GUI-вікно, не консоль) і виводить у ньому список назв (заголовків) усіх
вікон, які реально видно на робочому столі — на всіх підключених
моніторах.

**Вимоги:**
- Використати `EnumWindows` для перебору топ-рівневих вікон.
- Відфільтрувати: невидимі вікна (`IsWindowVisible == false`), вікна без
  заголовка, службові/приховані вікна оболонки (наприклад, `Program
  Manager`, вікна з нульовим розміром, cloaked-вікна через
  `DWMWA_CLOAKED` — актуально для UWP/сучасних застосунків).
- Список виводиться в простий `ListBox` або подібний контрол у вікні
  застосунку.
- Ніякого збереження даних на цьому етапі — лише відображення.

**Критерій готовності:** запуск `.exe` показує вікно зі списком назв
поточних видимих вікон, список відповідає тому, що реально відкрито на
робочому столі (перевіряється вручну користувачем).

### Етап 3.2 — Збереження поточного стану у файл

**Мета:** додати можливість зберегти поточний список вікон (назва, шлях
до виконуваного файлу, координати, розмір) у `.json`/`.xml` файл поруч із
`.exe`.

**Вимоги:**
- Для кожного вікна зі списку з етапу 3.1 додатково зібрати:
  - шлях до `.exe`, з якого запущено процес;
  - координати вікна (`left, top, right, bottom` або `x, y, width,
    height`);
  - стан вікна (normal / maximized / minimized);
  - ідентифікатор монітора, на якому знаходиться вікно (для коректного
    відновлення в multi-monitor конфігурації);
  - клас вікна (`GetClassName`) — додатково допомагає при пошуку вікна
    після перезапуску.
- Кнопка `Save session` в інтерфейсі є єдиним способом запису поточного
  списку у файл `session.json` поруч із `.exe`.
- Визначити та задокументувати JSON-схему файлу сесії (приклад нижче).

**Приклад структури `session.json`:**
```json
{
  "version": 1,
  "savedAt": "2026-08-22T12:00:00Z",
  "windows": [
    {
      "title": "Untitled - Notepad",
      "className": "Notepad",
      "exePath": "C:\\Windows\\System32\\notepad.exe",
      "state": "normal",
      "x": 100,
      "y": 100,
      "width": 800,
      "height": 600,
      "monitorIndex": 0
    }
  ]
}
```

**Критерій готовності:** після натискання "Зберегти" поруч із `.exe`
з'являється коректний файл з усіма видимими вікнами і правильними
даними.

### Етап 3.3 — Читання файлу та десеріалізація

**Мета:** навчити програму зчитувати збережений файл сесії при запуску і
перетворювати JSON/XML у внутрішні об'єкти даних (структури/класи
C++).

**Вимоги:**
- Створити структуру даних `WindowRecord` (title, className, exePath,
  state, x, y, width, height, monitorIndex).
- При старті програми, якщо файл сесії існує поруч із `.exe`, автоматично
  зчитати останню сесію та розпарсити її в `std::vector<WindowRecord>`.
- Додати окрему кнопку `Load session`, яка повторно завантажує список саме
  з `session.json`, не перечитуючи поточні процеси та не змінюючи файл.
- Обробка помилок: пошкоджений файл, відсутні поля, невідома версія
  схеми — не повинні валити програму, лише повідомлення про помилку.
- На цьому етапі дані ще не відображаються і не використовуються для
  запуску — лише перевірка коректності парсингу (наприклад, через
  вивід у консоль/лог або debug-вивід).

**Критерій готовності:** програма зчитує раніше збережений файл без
помилок, і всі поля відповідають тому, що було записано на етапі 3.2.

### Етап 3.4 — Відновлення позицій вікон за списком

**Мета:** об'єднати попередні етапи — програма при старті читає файл
минулої сесії й показує список збережених записів. При натисканні на
пункт списку — намагається запустити відповідну програму та розставити
її вікно згідно з координатами й розміром із файлу.

**Вимоги:**
- Список у вікні програми після старту формується з останньої сесії,
  автоматично завантаженої з файлу, або після натискання `Load session`.
- Додати окрему кнопку `Refresh threads`, яка перебудовує список виключно
  з поточних видимих вікон/процесів через `EnumWindows`; вона не читає
  `session.json` і не записує його.
- При виборі пункту:
    1. Перевірити, чи вже запущено процес з таким `exePath` — якщо так,
      використати його видиме вікно; збіг заголовка та класу не вимагати.
  2. Якщо не запущено — викликати `CreateProcess` зі збереженим шляхом.
    3. Знайти видиме вікно щойно запущеного процесу (через
      `GetWindowThreadProcessId` у зворотному напрямку — перебір вікон і
      порівняння PID). Для кількох записів одного процесу призначати різні
      вікна, а якщо їх недостатньо — запускати додатковий екземпляр.
  4. Викликати `SetWindowPos` із збереженими координатами й розміром,
     врахувати збережений стан (maximized/minimized/normal) через
     `ShowWindow`.
- Додати можливість "Відновити всі" — пройтись по всьому списку
  автоматично.

**Критерій готовності:** вибір запису зі списку призводить до запуску
(або активації) відповідної програми та коректного позиціонування її
вікна відповідно до збережених даних.

### Етап 3.5 — Затримка/очікування перед позиціонуванням

**Мета:** вирішити проблему програм, які не готові одразу прийняти
`SetWindowPos` (splash screen, довге завантаження, асинхронна
ініціалізація вікна).

**Вимоги:**
- Після `CreateProcess` використовувати `WaitForInputIdle` як перший
  рівень очікування.
- Додатково реалізувати polling-цикл: періодично (наприклад, кожні
  100–200 мс, з таймаутом ~10–15 с) перевіряти появу вікна з очікуваним
  класом/PID і лише тоді застосовувати `SetWindowPos`.
- Передбачити retry-логіку: якщо вікно з'явилось, але одразу після
  позиціонування "стрибнуло" назад (через власну ініціалізацію
  програми — типово для деяких застосунків), повторити спробу
  позиціонування ще раз через невелику паузу.
- Зробити параметри очікування (таймаут, інтервал polling) легко
  налаштовуваними (константи або конфігураційні поля).

**Критерій готовності:** відновлення сесії коректно працює навіть для
програм із помітною затримкою запуску (перевіряється на 2–3 реальних
прикладах застосунків із повільним стартом).

## 4. Наступні заплановані етапи (орієнтовний бэклог, після 3.5)

Ці етапи плануються **після** підтвердження завершення етапу 3.5 і
будуть деталізовані окремо перед початком роботи

1. **Кілька профілів сесій** — можливість зберігати/завантажувати
   декілька іменованих файлів сесій (не лише один `session.json`), вибір
   профілю через інтерфейс.
2. **Автоматичне збереження** — періодичне або за подією (закриття
   програми) автозбереження поточного стану.
3. **Гарячі клавіші (global hotkeys)** — виклик збереження/відновлення
   без відкриття головного вікна.
4. **Іконка в системному треї** — робота у фоні, мінімізація в трей.
5. **Список винятків** — можливість ігнорувати певні вікна/процеси при
   збереженні (наприклад, самого себе, системні утиліти).
6. **DPI-awareness** — коректна робота координат при різних масштабах
   (100%/125%/150% тощо) та при змінному складі моніторів.
7. **Обробка прав адміністратора** — коректна взаємодія з вікнами
   процесів, запущених з підвищеними правами (обмеження WinAPI без
   відповідних прав у самої утиліти).
8. **UI-покращення** — редагування записів сесії вручну (зміна
   координат/розміру перед відновленням), drag&drop впорядкування.
9. **Відновлення папок Explorer** — зберігати шлях до папки, яку мав
  відкритою кожен екземпляр Explorer на момент збереження, і запускати
  кожне вікно Explorer саме з відповідною папкою під час відновлення.
10. **Логування та діагностика** — лог-файл для налагодження випадків,
   коли позиціонування не спрацювало.

## 5. Процесний протокол для агента/асистента

- Усі написи користувацького інтерфейсу (заголовки вікон, кнопки, пункти
  меню, повідомлення тощо) мають бути виключно англійською мовою.
- Кожен етап реалізується окремим, чітко обмеженим кроком коду.
- Перед початком роботи над етапом — коротко підтвердити скоуп із
  цього документа.
- Після завершення етапу — надати результат (код + короткий опис, як
  зібрати й перевірити) і **зупинитись, чекаючи підтвердження**
  користувача.
- Не переходити до наступного етапу (включно з пунктами з розділу 4)
  без явного дозволу.
- Будь-які відхилення від цього документа (зміна стеку, додавання
  залежностей, зміна формату файлу сесії) — узгоджувати з користувачем
  окремо, а після узгодження — відображати зміну в цьому файлі та в
  ідентичному `claude.md`.

## Додатковий сценарій керування списком:

- користувач виділяє пункт у списку;
- натискання `Delete` або кнопки `Exclude selected` прибирає цей запис зі списку на поточний сеанс;
- після `Exclude selected` список змінюється лише в пам'яті поточного сеансу;
- `Load session` відновлює список із останнього збереженого `session.json`;
- `Refresh threads` будує актуальний список із поточних видимих вікон/процесів,
  уже без виключених записів;
- тільки `Save session` зберігає поточний список у `session.json`;
- цей механізм потрібен для ручного відсіву службових/небажаних вікон перед збереженням або відновленням сесії.

**Status bar:**
- між списком і кнопками має бути окремий `label` для всіх статусів роботи програми;
- інформаційні повідомлення відображаються синім кольором;
- успішні операції відображаються зеленим кольором;
- помилки відображаються червоним кольором;
- статуси завантаження, збереження, оновлення списку, виключення та відновлення
  вікон виводяться в status bar, а не через робочі модальні повідомлення.

### Останній етап — ООП-рефакторинг

**Мета:** реорганізувати реалізацію в чисту об'єктно-орієнтовану структуру
без зміни поведінки програми, формату `session.json` або появи зовнішніх
залежностей.

**Вимоги:**
- відокремити модель запису вікна, один клас `Json` для парсингу та
  серіалізації, `SessionSerializer`, сервіс роботи з вікнами та Win32 UI;
- не створювати окремі `JsonReader` і `JsonWriter`: читання та запис JSON
  мають залишатися в одному `Json` класі, допускаються статичні методи;
- Win32 callback-и, створення контролів, обробка подій і message loop мають
  бути відповідальністю окремого UI-класу;
- не створювати зайві класи: кожен клас повинен мати одну чітку роль, а
  прості перетворення та константи залишати функціями/типами відповідного
  сервісу;
- зберегти статичне лінкування, C++17, Win32 API та один `.exe`;
- після рефакторингу обов'язково зібрати Debug і Release та перевірити
  діагностику без зміни користувацької поведінки.
